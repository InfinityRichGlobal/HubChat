## ติดตั้งครั้งแรก — 6 ขั้น

> ทำตามลำดับ ห้ามข้าม ถ้าติดตรงไหนให้หยุดตรงนั้นแล้วบอก

### ขั้น 1 — ลงโปรแกรมที่ต้องใช้

ต้องมี **Node.js เวอร์ชัน 20 ขึ้นไป** ในเครื่อง
เช็คด้วยคำสั่ง `node -v` ถ้าไม่มีให้โหลดจาก nodejs.org

```bash
git clone https://github.com/InfinityRichGlobal/HubChat.git
cd HubChat
npm install
```

### ขั้น 2 — สร้างโปรเจกต์ Supabase

1. เข้า supabase.com → **New project**
2. ตั้งชื่อ `hubchat` เลือก region **Southeast Asia (Singapore)** — ใกล้ไทยที่สุด
3. ตั้ง Database Password แล้ว**จดไว้**
4. รอสร้างเสร็จประมาณ 2 นาที

### ขั้น 3 — สร้างตารางทั้งหมด

1. ใน Supabase เมนูซ้าย → **SQL Editor** → **New query**
2. เปิดไฟล์ `supabase/migrations/0001_init.sql` ในโปรเจกต์นี้
3. **คัดลอกทั้งไฟล์** ไปวางในช่อง แล้วกด **Run** (มุมขวาล่าง)
4. ต้องขึ้น `Success. No rows returned`
5. ทำซ้ำกับไฟล์ที่เหลือ **ตามลำดับเลข ห้ามข้าม ห้ามสลับ** :

```
0002_policy_engine.sql
0003_messaging_hardening.sql
0004_function_search_path.sql
0005_ingest.sql
0006_inbox.sql
0007_admin_tools.sql
0008_orders.sql
0009_autoreply_shipping.sql
0010_media_assets.sql
0011_tracking_import.sql
0012_dashboard_comments.sql
0013_notifications.sql
```

> 🔴 **ต้องรันให้ครบทุกไฟล์** ไฟล์หลัง ๆ แก้ไขของที่ไฟล์ก่อนหน้าสร้างไว้
> ถ้ารันไม่ครบ ระบบจะพังแบบหาสาเหตุยาก (เช่นเปิดหน้าออเดอร์ / หน้าคอมเมนต์ / หน้าแจ้งเตือน แล้วขึ้น error 500)

> ไฟล์พวกนี้รันซ้ำได้ ไม่พัง และมีตัวตรวจตัวเองอยู่ท้ายไฟล์
> ถ้ามีอะไรผิดจะขึ้น error ทันที ไม่ปล่อยผ่านครึ่ง ๆ กลาง ๆ
> ถ้าไม่แน่ใจว่ารันครบ กด Run ใหม่ทั้งหมดตามลำดับได้เลย

**วิธีเช็คว่าครบไหม** : รัน `npm run check-db` ในเทอร์มินัล

### ขั้น 4 — ใส่ค่าตั้งระบบ

```bash
cp .env.example .env.local
```

เปิดไฟล์ `.env.local` แล้วเติมค่า :

**จาก Supabase → Project Settings → API**

| ช่องใน .env.local | เอามาจาก |
|---|---|
| `NEXT_PUBLIC_SUPABASE_URL` | Project URL |
| `NEXT_PUBLIC_SUPABASE_ANON_KEY` | anon / public key |
| `SUPABASE_SERVICE_ROLE_KEY` | service_role key (กด Reveal ก่อน) |

**สร้างเองด้วยคำสั่ง** (macOS / Linux เปิด Terminal, Windows ใช้ Git Bash)

```bash
openssl rand -base64 48    # เอาค่าที่ได้ไปใส่ SESSION_SECRET
openssl rand -base64 32    # เอาค่าที่ได้ไปใส่ ENCRYPTION_KEY
```

**บัญชีเจ้าของ** — เติม 3 บรรทัดนี้

```
OWNER_NAME=ชื่อคุณ
OWNER_EMAIL=อีเมลที่จะใช้ล็อกอิน
OWNER_PASSWORD=รหัสชั่วคราว        # เว้นว่างไว้ก็ได้ ระบบจะสุ่มให้
```

### ขั้น 5 — ตรวจว่าต่อติดแล้วสร้างบัญชีเจ้าของ

```bash
npm run check-db      # ต้องขึ้น ✅ ครบทั้ง 26 ตาราง
npm run create-owner  # สร้างบัญชีเจ้าของ — รันได้ครั้งเดียว
```

รันเสร็จแล้ว **ลบ `OWNER_NAME` / `OWNER_EMAIL` / `OWNER_PASSWORD` ออกจาก `.env.local`**

### ขั้น 6 — เปิดใช้งาน

```bash
npm run dev
```

เปิด <http://localhost:3000> → เข้าสู่ระบบด้วยอีเมลกับรหัสชั่วคราว
ระบบจะบังคับให้ตั้งรหัสผ่านใหม่ทันที

## Message Policy Engine (รอบ 2)

### ทำไมต้องมี

Meta มีกฎว่า "ส่งข้อความหาลูกค้าตอนไหนได้บ้าง" และกฎนี้เปลี่ยนบ่อยมาก
ถ้าเขียนกฎกระจายไว้ในหน้าแชท ในบอท ในตัวส่ง follow-up
พอ Meta เปลี่ยนกฎทีต้องไล่แก้ทุกที่ และมักลืมบางจุดจนส่งผิดนโยบาย → เพจโดนระงับ

ระบบนี้จึงรวมกฎทั้งหมดไว้ที่เดียว แล้วบังคับให้ทุกการส่งวิ่งผ่านทางเดียว

### เส้นทางของข้อความ

```
แอดมินกดส่ง / บอทตอบคีย์เวิร์ด / scheduler ส่ง follow-up
                         │
                         ▼
        sendMessage()  ← ทางเข้าเดียว ไม่มีทางอื่น
                         │
                         ├─ 1. กันส่งซ้ำ (idempotency_key)
                         ├─ 2. ดึงข้อเท็จจริงจากฐานข้อมูล
                         │
                         ▼
              Message Policy Engine  ← กฎของ Meta อยู่ที่นี่ที่เดียว
                         │
             ┌───────────┴───────────┐
        ส่งไม่ได้                 ส่งได้
             │                       │
             │                       ▼
             │            เลือก transport ให้เอง
             │            STANDARD → HUMAN_AGENT → UTILITY → MARKETING
             │                       │
             │                       ▼
             │              Transport Adapter (ประกอบ payload)
             │                       │
             │                       ▼
             │              Meta client กลาง  ← ที่เดียวที่ยิง graph.facebook.com
             │                       │
             ▼                       ▼
      บันทึก send_attempts    บันทึก send_attempts
      + เหตุผลภาษาไทย        + retry เฉพาะ error ชั่วคราว
      (ไม่ยิงออกไปเลย)        + แก้ข้อมูลให้ตรงความจริงถ้า Meta บอกว่ากรอบเวลาปิดแล้ว
```

### กฎที่ระบบบังคับให้ ไม่ต้องจำเอง

| กฎ | บังคับด้วยอะไร |
|---|---|
| ทุกการส่งต้องผ่าน engine | มีทางเข้าเดียวคือ `sendMessage()` + eslint + เทสต์สถาปัตยกรรม |
| ห้ามเรียก Meta ตรง ๆ | `graph.facebook.com` มีได้แค่ในไฟล์เดียว มีเทสต์ไล่ตรวจทั้งโปรเจกต์ |
| ห้ามฝังกฎ 24 ชม. ไว้ที่อื่น | ตัวเลขอยู่ใน `policy/config.ts` ที่เดียว มีเทสต์ตรวจว่าไม่มีที่อื่น |
| แอดมินห้ามเลือก transport เอง | API ไม่คืนชื่อ transport ให้หน้าเว็บเลือก มีเทสต์ตรวจ |
| บอท/scheduler ห้ามใช้ `HUMAN_AGENT` | ตรวจ 2 ชั้น (engine + adapter) มีเทสต์ 5 ข้อ |
| ห้ามแปลงข้อความขายให้เนียนเป็นช่องอื่น | ตารางประเภทข้อความต่อช่องทาง มีเทสต์แยกต่างหาก |
| ห้าม retry error เชิงนโยบาย | ตัวแยกประเภท error + เทสต์ครบทุกรหัส |
| ห้ามใช้ message tag แบบเก่า | เทสต์ไล่ตรวจทั้งโปรเจกต์ว่าไม่มีชื่อ tag เหล่านั้น |
| Messenger กับ Instagram ไม่เหมือนกัน | ค่าตั้งแยกกันคนละชุด มีเทสต์ตรวจว่าไม่รั่วถึงกัน |

### ค่าเริ่มต้นคือ "ปิดก่อน"

เปิดใช้แค่การส่งปกติในกรอบเวลาเท่านั้น
ช่องทางที่เหลือปิดไว้หมด และต้องผ่าน 2 สวิตช์ถึงจะใช้ได้ :

1. `..._ENABLED=true` — เปิดใช้
2. `..._VERIFIED=true` — ยืนยันแล้วว่าอ่านเอกสาร Meta และได้รับอนุมัติจริง

ตั้งอย่างเดียวไม่พอ ต้องครบทั้งสอง — กันเผลอเปิดทั้งที่ยังไม่ได้รับอนุมัติ

ดูรายการที่ต้องยืนยันก่อนเปิดได้ที่ `DEFERRED_REVIEW.md`

## ความปลอดภัยของการส่งข้อความ (รอบ 2.1)

หลังตรวจสอบโดยผู้ตรวจอิสระ พบ 4 จุดที่ยังเสี่ยง และแก้แล้วทั้งหมด

### 1. กันส่งซ้ำ — ให้ฐานข้อมูลเป็นคนตัดสิน

เดิมโค้ดทำแบบ "ดูก่อนว่าเคยส่งไหม → ไม่เคย → ยิง → บันทึก"
ถ้าสองคำขอมาพร้อมกัน ทั้งคู่ผ่านด่าน "ดูก่อน" แล้วยิงทั้งคู่ → ลูกค้าได้ข้อความซ้ำ

ตอนนี้ทุกการส่งต้อง **จองสิทธิ์กับฐานข้อมูลก่อน** ผ่านตาราง `message_sends`
ที่มี unique index บนกุญแจกันซ้ำ มีคำขอเดียวเท่านั้นที่จองสำเร็จและได้ยิง
ที่เหลือรู้ตัวทันทีว่าแพ้ และไม่ยิงเลย

> ทดสอบจริงแล้ว: ยิง 5 คำขอพร้อมกันด้วยกุญแจเดียวกัน → Meta ถูกเรียกครั้งเดียว

### 2. กรณีไม่รู้ผล — ห้ามลองใหม่

ถ้าคำขอออกไปแล้วไม่ได้รับคำตอบ (timeout / เน็ตขาด) เราไม่มีทางรู้ว่า Meta รับไปแล้วหรือยัง
การลองใหม่ในสถานการณ์นี้ = ลูกค้าอาจได้ข้อความซ้ำ ซึ่งแก้ไม่ได้

ระบบจึงแยกกรณีนี้ออกมาเป็น `outcome_unknown` : หยุดทันที ไม่ลองใหม่
บันทึกไว้ให้คนเปิดดูเอง แล้วตัดสินใจว่าจะส่งซ้ำไหม

> เราเลือกฝั่ง **"ส่งขาดดีกว่าส่งซ้ำ"** เพราะ Meta ไม่ได้รับประกันว่าจะส่งครั้งเดียวให้เรา

### 3. "คนพิมพ์เอง" ต้องพิสูจน์ได้

เดิมผู้เรียกส่ง `human_typed: true` เข้ามาเองได้ แปลว่าโค้ดอัตโนมัติตัวไหนก็อ้างเป็นคนได้
ซึ่งอันตราย เพราะ `HUMAN_AGENT` ใช้ได้เฉพาะข้อความที่คนพิมพ์จริง

ตอนนี้ต้องใช้ **ตั๋วรับรองแหล่งที่มา** ที่สร้างได้จาก `provenance.ts` ไฟล์เดียว
และตั๋วของ "คน" สร้างได้เฉพาะตอนมี session ของแอดมินตัวจริงเท่านั้น
งานเบื้องหลังไม่มี cookie จึงสร้างไม่ได้โดยธรรมชาติ

### 4. คำตอบของ Meta ห้ามลบประวัติข้อความจริง

เดิมพอ Meta ตอบว่าส่งไม่ได้ ระบบไป **ลบ** `last_customer_message_at` ทิ้ง
นั่นคือการทำลายหลักฐานว่าลูกค้าเคยทักมาเมื่อไหร่ และทำให้รายงานผิดตามไปด้วย

ตอนนี้แยกเป็นสองอย่างคนละตาราง:

| | เก็บที่ไหน | คืออะไร |
|---|---|---|
| ลูกค้าทักมาเมื่อไหร่ | `conversations` / `customers` | **ข้อเท็จจริง** — ห้ามแก้ |
| Meta บอกว่าส่งไม่ได้เมื่อไหร่ | `conversation_policy_state` | **สิ่งที่เราสังเกตเห็น** |

Policy Engine อ่านทั้งคู่: ถ้า Meta เคยปฏิเสธหลังข้อความล่าสุดของลูกค้า → ไม่ส่ง
แต่ถ้าลูกค้าทักกลับมาทีหลัง ข้อสังเกตเก่าถือว่าใช้ไม่ได้แล้ว

### 5. เครื่องจริงเปิดช่องทางที่ยังไม่ยืนยันไม่ได้

ถ้า `NODE_ENV=production` และมี `POLICY_ALLOW_UNVERIFIED_TRANSPORTS=true`
ระบบจะ **ไม่ยอมสตาร์ต** พร้อมบอกวิธีแก้เป็นภาษาไทย

### 6. ข้อมูลต้องสัมพันธ์กันจริง

`sendMessage()` รับแค่ **รหัสห้องแชท** อย่างเดียว
ลูกค้าคนไหน เพจไหน ช่องทางไหน ปลายทางคือใคร — ระบบไปอ่านจากฐานข้อมูลเอง
แล้วตรวจว่าทุกอย่างสัมพันธ์กัน ไม่ตรงข้อเดียวก็ไม่ส่ง

### 7. ตามรอยย้อนหลังได้ครบ

| ตาราง | หนึ่งแถวคือ |
|---|---|
| `message_sends` | การส่งหนึ่งครั้งในเชิงตรรกะ + ผลสุดท้าย + `meta_message_id` |
| `send_attempts` | หนึ่งครั้งที่ยิงออกไปจริง (retry 3 ครั้ง = 3 แถว ไม่ทับกัน) |

ตอบได้ว่า: ส่งอะไร ใช้กุญแจไหน engine ตัดสินยังไง ใช้ช่องทางไหน
ยิงจริงกี่ครั้ง แต่ละครั้งเกิดอะไร Meta ให้ id อะไรมา และจบยังไง

## ทางเข้าของข้อมูล (รอบ 3A)

ก่อนหน้านี้ฐานข้อมูลว่างเปล่า เพราะยังไม่มีทางที่ข้อความจะไหลเข้ามา
รอบ 3A สร้างทางเข้านั้น

### เส้นทางของข้อความขาเข้า

```
ลูกค้าทักเข้าเพจ
   ↓
Meta ยิง webhook มาที่  POST /api/webhooks/meta
   ↓
1. ตรวจลายเซ็น X-Hub-Signature-256   ← ไม่ผ่าน = ปฏิเสธทันที ไม่ดูเนื้อหา
   ↓
2. วางลงตาราง webhook_queue
   ↓
3. ตอบ 200 กลับไปทันที               ← สเปกหัวข้อ 6.3 ตอบช้า = Meta ยิงซ้ำ
   ↓
--- ตอบไปแล้ว งานหนักเริ่มตรงนี้ ---
   ↓
4. แกะ JSON → เหตุการณ์กลาง          (src/server/ingest/parse.ts — ฟังก์ชันบริสุทธิ์)
   ↓
5. หาเพจในระบบจาก id ฝั่ง Meta        ← ไม่รู้จัก = ข้าม ไม่ทำให้คิวค้าง
   ↓
6. เรียกฟังก์ชันในฐานข้อมูล            (ingest_inbound_message / ingest_echo_message)
      • สร้าง/หาลูกค้า + ห้องแชท
      • ใส่ข้อความ แบบ "ซ้ำแล้วข้าม"    ← กันซ้ำที่ระดับฐานข้อมูล ไม่ใช่ระดับโค้ด
      • อัปเดตเวลา/ตัวอย่าง/ยังไม่อ่าน  เฉพาะตอนที่ข้อความใหม่จริง
   ↓
7. ดึงชื่อ+รูปโปรไฟล์จาก Meta (ครั้งเดียวต่อลูกค้า ล้มเหลวได้ ไม่ทำให้ข้อความหาย)
```

## หน้าแชท (รอบ 3B)

### ปุ่มส่งปุ่มเดียว

หน้าแชทมีปุ่มส่งปุ่มเดียว ไม่มีที่ไหนให้แอดมินเลือกช่องทางส่งเองเลย
เพราะการเลือกผิดคือส่วนที่ทำให้เพจโดนระงับ (สเปกหัวข้อ 6.1)

```
แอดมินพิมพ์ + กดส่ง
   ↓
POST /api/conversations/[id]/reply
   รับมาแค่ 2 อย่าง : ห้องไหน (จาก URL) + ข้อความว่าอะไร (จาก body)
   ↓
humanAdminReply()          ← ตราประทับ "คนพิมพ์เอง" ออกจาก session ไม่ใช่จาก body
   ↓
sendMessage()              ← ทางออกเดียวของการส่งข้อความ
   ↓
Policy Engine เลือกช่องทางเอง → adapter → Meta
   ↓
บันทึกลงประวัติแชทพร้อม meta_message_id
```

**สิ่งที่ route ตอบแชทตั้งใจไม่รับจากหน้าเว็บ** (มีชุดทดสอบคุมไว้) :
`transport` · `message_tag` · `messaging_type` · `customer_id` · `page_id` · `psid` · `provenance`

### ล็อกกันแอดมินชน (สเปก 5.1)

แอดมิน 2 คนกดเข้าห้องเดียวกันพร้อมกันได้จริง โค้ด JavaScript ตัดสินไม่ได้
จึงให้ฐานข้อมูลตัดสินในคำสั่งเดียว (`acquire_conversation_lock`)

- คนที่ได้ล็อกจะต่ออายุทุก 45 วินาทีระหว่างเปิดหน้าอยู่
- ปิดหน้าไป → ล็อกหมดอายุเองใน 3 นาที ไม่ค้างถาวร
- คนอื่นยัง "ตอบได้" แต่เห็นแถบเตือนว่าใครกำลังดูแลอยู่ (ไม่ใช่การห้ามพิมพ์)

## เครื่องมือแอดมิน (รอบ 4)

รอบนี้ **ไม่มีการส่งข้อความหาลูกค้าเพิ่มขึ้นเลยแม้แต่เส้นทางเดียว** โดยตั้งใจ
ทุกอย่างเป็นตัวช่วยให้แอดมินทำงานเร็วขึ้น แต่ยังต้องกดส่งเองเสมอ

| เครื่องมือ | ใช้ยังไง |
|---|---|
| **ชุดคำตอบ** | พิมพ์ `/` ในช่องพิมพ์ → ค้นทันที → Enter หรือแตะเพื่อวางลงช่อง |
| **เมนูแตะข้อความ** | แตะฟองข้อความ 1 ครั้ง → คัดลอกไปช่องพิมพ์ / ยกมาอ้างอิง / ดึงที่อยู่+เบอร์ / คัดลอก |
| **ปัดขวา** | ปัดฟองข้อความไปทางขวา → ยกมาอ้างอิงทันที |
| **ดึงที่อยู่อัตโนมัติ** | regex ล้วน ไม่ใช้ AI (สเปก 5.2) — กรอกให้ล่วงหน้า แล้วแอดมินตรวจก่อนบันทึก |
| **แท็ก** | ติดแท็กในห้องแชท แล้วกรองในลิสต์ได้ |

### 🔴 กฎที่บังคับด้วยชุดทดสอบ

- ชั้นชุดคำตอบ/แท็ก **ห้าม** เรียก `sendMessage()` หรือแตะ Meta เลย
  (ชุดคำตอบคือข้อความสำเร็จรูป ไม่ใช่การตอบอัตโนมัติ)
- ตัวดึงที่อยู่ต้องเป็นฟังก์ชันบริสุทธิ์ — ห้ามต่อฐานข้อมูล ห้ามยิงเน็ต ห้ามอ่านเวลาปัจจุบัน
- ไม่มีเส้นทางไหนเอาผลจากตัวดึงไปเขียนลงตาราง `customers` โดยตรง
  ค่าที่บันทึกต้องผ่านฟอร์มที่แอดมินตรวจแล้วเท่านั้น (สเปก 5.2 เขียนไว้ตัวหนา)

### สิ่งที่รับประกันไว้ และมีชุดทดสอบยืนยัน

## ออเดอร์ + สินค้า + โปรโมชัน (รอบ 5)

รอบนี้ก็ยัง **ไม่มีการส่งข้อความหาลูกค้าเพิ่มขึ้นเลยแม้แต่เส้นทางเดียว**
สร้างออเดอร์แล้วระบบเงียบสนิท — ถ้าจะบอกลูกค้า แอดมินพิมพ์ส่งเองในห้องแชท

| ส่วน | ใช้ยังไง |
|---|---|
| **ตั้งค่า → สินค้า + โปรโมชัน** | ตั้งชื่อ/สี/ราคาสินค้า และรูปแบบโปร (เดี่ยว / แพ็ก / ซื้อ X แถม Y / บ็อกซ์เซ็ต) |
| **ปุ่มตะกร้าในห้องแชท** | เลือกโปร → จิ้มสี → ราคาขึ้นเอง → ที่อยู่เติมให้จากข้อมูลลูกค้า → กดสร้าง |
| **หน้าออเดอร์** | ค้นด้วยเลขออเดอร์/ชื่อ/เบอร์/เลขพัสดุ · กรองสถานะและเพจ |
| **รายละเอียดออเดอร์** | แก้สถานะ/การจ่ายเงิน · กรอกขนส่ง+เลขพัสดุ · **ปุ่มคัดลอกที่อยู่** · ประวัติแก้ไข |

### 🔴 กฎที่บังคับด้วยชุดทดสอบ

- **สูตรราคามีที่เดียว** คือ `calculateOrder()` ฝั่งเซิร์ฟเวอร์
  เบราว์เซอร์ส่งได้แค่ "เลือกอะไรบ้าง" ไม่ใช่ "ราคาเท่าไหร่"
  ราคาที่เห็นบนจอมาจาก `/api/orders/preview` ซึ่งเรียกฟังก์ชันตัวเดียวกับตอนบันทึกจริง

## ตอบอัตโนมัติด้วยคีย์เวิร์ด (รอบ 6)

🔴 **รอบนี้คือครั้งแรกที่ระบบส่งข้อความหาลูกค้าเองโดยไม่มีคนกดปุ่ม**

| ส่วน | ใช้ยังไง |
|---|---|
| **ตั้งค่า → ตอบอัตโนมัติ** | ตั้งคีย์เวิร์ด + ข้อความตอบ + ลำดับ · เปิด/ปิดทีละกฎ · ดูประวัติที่บอทตอบไปจริง |
| **วิธีเทียบ** | มีคำนี้อยู่ในข้อความ / ตรงทั้งข้อความ / ขึ้นต้นด้วยคำนี้ |
| **ขอบเขต** | ผูกเฉพาะบางเพจ หรือใช้ทุกเพจก็ได้ |

### 🔴 กฎที่บังคับด้วยชุดทดสอบ

- **หนึ่งข้อความขาเข้า = ตอบอัตโนมัติได้ครั้งเดียวตลอดกาล**
  บังคับด้วย `unique index` บน `auto_reply_executions(message_id)` — ไม่ใช่โค้ด JavaScript
  worker 2 ตัวยิงพร้อมกันก็ยังตอบครั้งเดียว (มีเทสต์ยิงพร้อมกัน 4 เส้นพิสูจน์)
- **ต้องผ่าน Policy Engine เสมอ** — ชั้นตอบอัตโนมัติ import Meta client / transport ไม่ได้เลย
- **ห้ามใช้ HUMAN_AGENT เด็ดขาด** — ใช้ตราประทับ `keywordBotProvenance()` ซึ่ง `human_authored = false`
  พ้นกรอบ 24 ชม. = ไม่ส่ง ไม่มีการยกระดับช่องทางเพื่อให้ส่งได้
- **ผลลัพธ์ "ไม่ทราบผล" ห้ามลองใหม่อัตโนมัติ** (`maxRetries: 1`)
- **ไม่มี regex ที่แอดมินกำหนดเอง** — กันช่อง ReDoS ตั้งแต่ออกแบบ
- **สำเนากฎถูกจดไว้ทุกครั้งที่ตอบ** — แก้กฎทีหลังแล้วยังตอบได้ว่าตอนนั้นส่งอะไรไป

### ตัวจับคีย์เวิร์ดกับภาษาไทย

ใช้ **NFKC** ไม่ใช่ NFC — เพราะ `ำ` กับ `ํ`+`า` มองด้วยตาเหมือนกันแต่ NFC ไม่รวมให้
(ตรงนี้เคยเขียนผิดแล้วชุดทดสอบจับได้) และ NFKC ยังแปลงตัวอักษรเต็มความกว้างจากคีย์บอร์ดมือถือให้ด้วย

## เก็บรูปและสลิปไว้เองอย่างถาวร (D-17 — ปิดแล้ว ✅)

🔴 **ปัญหาที่แก้** : รูปที่ลูกค้าส่งมาใช้ลิงก์ชั่วคราวของ Meta ซึ่งหมดอายุ
พอหมดอายุแล้วเปิดย้อนหลังไม่ได้ — และ **สลิปโอนเงินคือหลักฐานการชำระเงิน**

**ทางแก้** : ดาวน์โหลดมาเก็บที่ Cloudflare R2 ทันทีที่รับ webhook ก่อนลิงก์จะหมดอายุ

| ส่วน | ทำอะไร |
|---|---|
| **รับเข้า** | ไฟล์แนบทุกก้อนถูกโหลดเก็บทันที — ทำ **ก่อน** ตอบอัตโนมัติ เพราะลิงก์เดินนาฬิกาอยู่ |
| **แสดงผล** | หน้าแชทใช้สำเนาของเราก่อนเสมอ (`/api/media/…`) ลิงก์ Meta เป็นแค่ทางสำรอง |
| **สลิป** | หน้าออเดอร์มีปุ่มแนบสลิป เก็บถาวร ผูกกับออเดอร์ พร้อมประวัติการแก้ไข |

### 🔴 กฎที่บังคับด้วยชุดทดสอบ

- **หนึ่งไฟล์แนบ = โหลดครั้งเดียวตลอดกาล** — `unique index (message_id, attachment_index)`
  worker หลายตัวพร้อมกันก็โหลดครั้งเดียว (มีเทสต์ยิงพร้อมกัน 4 เส้น)
- **ต้องจองสิทธิ์กับฐานข้อมูลก่อนโหลดเสมอ**
- **ถังไม่เปิดสาธารณะ** — เสิร์ฟผ่าน `/api/media/[id]` ที่ตรวจสิทธิ์รายเพจทุกครั้ง
- **กุญแจ R2 อยู่ฝั่งเซิร์ฟเวอร์เท่านั้น** — ห้ามหลุดไปเบราว์เซอร์
- ⭐ **ระบบทำงานได้แม้ยังไม่ตั้งค่า R2** — จดเป็น `skipped` แล้วเดินต่อ ไม่พัง
- **การเก็บไฟล์ล้มเหลว ต้องไม่ทำให้ข้อความลูกค้าหาย**

### สถานะของไฟล์แต่ละก้อน

| status | แปลว่า |
|---|---|
| `stored` | ✅ เปิดได้ตลอดไป |
| `skipped` | ยังไม่ได้ตั้งค่า R2 ตอนไฟล์เข้ามา |
| `expired` | 🔴 ลิงก์หมดอายุก่อนเก็บทัน — กู้ไม่ได้ |
| `failed` | เก็บไม่สำเร็จ แต่ยังไม่ถึงกับกู้ไม่ได้ |

⚙️ **ตั้งค่า** : [docs/STORAGE.md](docs/STORAGE.md) — ฟรี 10 GB/เดือน ทำครั้งเดียวจบ

## ดึงแชทเก่าจาก Meta (รอบ 7)

**เปิดระบบมาแล้วเห็นแต่แชททดสอบ — ไม่ใช่ระบบพัง**
Meta ส่ง webhook ให้เฉพาะข้อความที่เกิด **หลังจาก** เชื่อมเพจเท่านั้น
แชทเก่าไม่ไหลเข้ามาเอง ต่อให้รอเป็นเดือน ต้องไปดึงเอง

**วิธีใช้** : ตั้งค่า → จัดการเพจ → ปุ่ม **"ดึงแชทเก่าเข้าระบบ"**

### 🔴 กฎที่บังคับด้วยชุดทดสอบ

- **กดซ้ำได้ไม่จำกัด** — ใช้ฟังก์ชันบันทึกตัวเดียวกับ webhook
  จึงกันซ้ำได้ฟรีด้วย `meta_message_id` และไม่มีเส้นทางบันทึกเส้นที่สอง
- **ทยอยดึงเป็นชุด ไม่ดึงรวดเดียวจนหมด** — ยิงรัวจะชนโควตา Meta
  แล้ว **ข้อความจริงของลูกค้าจะเข้าไม่ได้ด้วย** ซึ่งเสียหายกว่าที่ได้
- **ห้องที่ Meta บอกว่าอ่านแล้ว ต้องไม่เด้งเป็น "ยังไม่ตอบ"**
  แต่ต้องไม่กลบข้อความที่เพิ่งเข้ามาระหว่างซิงก์

### ไล่อ่านประวัติย้อนหลัง

- ปุ่ม **"ดูข้อความเก่ากว่านี้"** ในห้องแชท / **"โหลดแชทเพิ่ม"** ในลิสต์
- **จอไม่กระชากลงล่างอีกแล้ว** ตอนกำลังเลื่อนขึ้นไปอ่านของเก่า
  (เดิมเด้งลงทุก 4 วินาที — เป็นสาเหตุหลักที่ใช้ยากกว่า Business Suite)
- ป้ายคั่นวัน / ปุ่มลงล่างสุด / เบอร์ลูกค้า + นาฬิกากรอบ 24 ชม. ที่หัวห้อง

### 🔴 กฎที่ฐานข้อมูลเป็นคนบังคับ (ไม่ใช่โค้ด)

### 🔴 การจับคู่ห้ามเดา

จับคู่ผิด = **ลูกค้าได้เลขพัสดุของคนอื่น = แก้ไม่ได้**
"ไม่แน่ใจ" จึงแปลว่า **"ให้คนเลือก"** เสมอ

| ลำดับ | วิธี | ผล |
|---|---|---|
| 1 | เลขออเดอร์ในช่องอ้างอิงของขนส่ง | ✅ อัตโนมัติ |
| 2 | เบอร์โทร (normalize แล้ว) เจอใบเดียว | ✅ อัตโนมัติ |
| 3 | เบอร์ + รหัสไปรษณีย์ตรงทั้งคู่ | ✅ อัตโนมัติ |
| 4 | เบอร์ตรง แต่เจอหลายใบ | ⚠️ แอดมินเลือก |
| 5 | ชื่อคล้าย + ไปรษณีย์ตรง | ⚠️ เสนอเท่านั้น |
| 6 | ไม่เจอ | ❌ ค้นเอง / ข้าม |

> 💡 **เคล็ดลับ** : ตอนสร้างใบปะหน้า ใส่เลขออเดอร์ของเราลงช่อง "อ้างอิง" ของขนส่ง
> → จับคู่แม่น 100% ไม่ต้องพึ่งเบอร์เลย

### 🔴 การแจ้งลูกค้า

- **ผ่าน `sendMessage()` → Policy Engine เท่านั้น** ไม่มีการยิง Meta จากโค้ดนำเข้า
- **`bulkJobProvenance`** → `human_authored = false` เสมอ → **ไม่มีวันได้ HUMAN_AGENT**
- **Policy ห้าม = จดว่า "ยังไม่ได้แจ้ง"** ไม่ใช่ฝืนส่งหรือปลอมว่าสำเร็จ
- **ไม่ทราบผล = ไม่ลองใหม่** และถือว่าแจ้งแล้ว (ยอมส่งขาด ดีกว่าส่งซ้ำ)
- **ใช้เลขพัสดุล่าสุดบนออเดอร์เสมอ** ไม่ใช่ค่าที่ถ่ายไว้ตอนเข้าคิว
- ทยอย 10 ข้อความ/นาที · ไม่รบกวน 22:00–08:00 · กดครั้งละไม่เกิน 40 ราย
- **เนื้อข้อความประกอบฝั่งเซิร์ฟเวอร์ ห้ามมีคำขาย** (มีเทสต์ไล่ตรวจคำต้องห้าม)

แยกตามแอด / เพจ / แอดมิน / สินค้าขายดี / รายวัน / รายชั่วโมง

**🔴 กฎที่บังคับด้วยชุดทดสอบ**

- **ออเดอร์ที่ยกเลิกไม่นับเป็นยอดขาย** — ทั้งยอดรวม ยอดเฉลี่ย และอัตราปิดการขาย
- **แอดมินที่มีสิทธิ์แค่ "ยอดของตัวเอง" จะไม่เห็นอัตราปิดการขาย** เลย
  แทนที่จะเห็นตัวเลขที่คำนวณจากฐานผิด — ซ่อนดีกว่าแสดงผิด
- **เวลาทั้งหมดคิดตามเวลาไทย** ไม่ใช่ UTC (ยอด "วันนี้" ต้องตรงกับวันของคนไทย)
- **ระยะเวลาปิดการขายที่ติดลบถูกทิ้ง** ไม่ให้ไปดึงค่าเฉลี่ยเพี้ยน

### ฟีดคอมเมนต์ (สเปก 5.5)

คอมเมนต์ใต้โพสต์ไหลเข้ามาทาง webhook เส้นเดียวกับข้อความ แต่ **เดินคนละสาย**

**🔴 กฎที่บังคับด้วยชุดทดสอบ**

- **บันทึกอย่างเดียว ไม่ตอบอัตโนมัติเด็ดขาด** แอดมินต้องกดเองทุกครั้ง
  ทั้งตอบใต้โพสต์และทักส่วนตัว
- **ทักส่วนตัวได้ครั้งเดียวต่อคอมเมนต์ตลอดกาล** (กฎของ Meta)
  บังคับด้วยการจองสิทธิ์ในฐานข้อมูล — สองคนกดพร้อมกันก็ยิงออกไปครั้งเดียว
- **คอมเมนต์เก่าเกิน 7 วัน → ปฏิเสธตั้งแต่ต้น** ไม่ยิงออกไปเปล่า ๆ
- **ไม่ทราบผล = ไม่คืนสิทธิ์** (ยอมเสียสิทธิ์ ดีกว่าลูกค้าได้ข้อความซ้ำ)
- **คำกรอง** (ราคา / สนใจ / cf / จอง / สั่ง) ปรับได้ในหน้าเว็บ
  ใช้ NFKC ปรับข้อความก่อนเทียบ ไม่งั้นสระไทยที่พิมพ์คนละแบบจะไม่แมตช์

## แจ้งเตือน (รอบ 10 — สเปก 6.7)

สองช่องทางทำงานคู่กัน เพราะแต่ละอันพังคนละแบบ :
**PWA Push** เด้งบนเครื่องของแต่ละคน · **Telegram** ส่งเข้ากลุ่มของร้าน

| เหตุการณ์ | ใครได้รับ |
|---|---|
| ลูกค้าทักใหม่ (ยังไม่มีคนรับ) | ทุกคนที่ดูเพจนั้น |
| ลูกค้าตอบในแชทที่ฉันรับไว้ | เฉพาะคนที่รับแชท |
| แชทเงียบเกิน 15 นาที | ทุกคนที่ดูเพจนั้น |
| ใกล้หมดกรอบ 24 ชม. | คนที่รับแชทไว้ |
| คอมเมนต์ที่เข้าคำกรอง | ทุกคนที่ดูเพจนั้น |

### 🔴 กฎที่บังคับด้วยชุดทดสอบ

- **เหตุการณ์เดียว คนเดียว ช่องทางเดียว = แจ้งได้ครั้งเดียว**
  บังคับด้วย unique index บน `dedupe_key` ไม่ใช่ด้วยโค้ด
- **แต่ลูกค้าเก่าที่กลับมาทักต้องได้แจ้งเตือนใหม่**
  (ห้องแชทหนึ่งห้องอยู่กับลูกค้าคนนั้นตลอดชีวิต — กุญแจกันซ้ำจึงต้องมี `message_id` ด้วย)
- **ส่งไม่สำเร็จ = กลับเข้าคิว ลองได้ 3 ครั้ง** ไม่ใช่หายตลอดกาล
- **Telegram รวบส่ง** 30 เหตุการณ์ = 1 ข้อความ ไม่ใช่ 30 ข้อความ
  และส่วนที่ล้นเพดานความยาว **คืนเข้าคิวรอบถัดไป** ไม่ใช่ทิ้งเงียบ ๆ
- **"บอทตอบ" ไม่นับว่า "คนตอบ"** และ **"เปิดอ่านแล้ว" ไม่นับว่า "ตอบแล้ว"**
- **แจ้งเตือนพังต้องไม่ทำให้ข้อความของลูกค้าหาย** ทุกจุดห่อ try/catch ไว้
- **ผู้ดู (viewer) ไม่ได้รับแจ้งเตือนเรื่องแชท** เพราะกดเข้ามาก็ตอบไม่ได้
- **`/api/notify/flush` ไม่เปิดให้ใครก็เรียก** ต้องมี `CRON_SECRET` หรือเป็นเจ้าของร้าน

### ⚠️ สองอย่างที่ต้องทำ ไม่งั้นแจ้งเตือนไม่ครบ

1. **สร้างกุญแจ** : `npm run vapid` แล้วเอาค่าไปใส่ `.env.local`
2. **ตั้งตัวเดินตรวจ** : `npm run notify` หรือ cron ยิง `POST /api/notify/flush` ทุก 5 นาที
   — ถ้าไม่ตั้ง จะได้แจ้งเตือนแค่ **3 ใน 5** เหตุการณ์ และไม่มีอะไรเตือนว่าขาด

### iPhone ต้องติดตั้งก่อน

Apple ไม่อนุญาตให้เว็บในแท็บ Safari ส่งแจ้งเตือน
ต้อง **แชร์ → เพิ่มไปยังหน้าจอโฮม → เปิดจากหน้าจอโฮม** ก่อนเท่านั้น
หน้าตั้งค่าจะตรวจแล้วขึ้นกล่องสอนวิธีให้เอง

📄 **วิธีใช้ทั้งหมด** : [docs/NOTIFICATIONS.md](docs/NOTIFICATIONS.md)
