## ติดตั้งครั้งแรก — 6 ขั้น

> ทำตามลำดับ ห้ามข้าม ถ้าติดตรงไหนให้หยุดตรงนั้นแล้วบอก

### ขั้น 1 — ลงโปรแกรมที่ต้องใช้

ต้องมี **Node.js เวอร์ชัน 20 ขึ้นไป** ในเครื่อง
เช็คด้วยคำสั่ง `node -v` ถ้าไม่มีให้โหลดจาก nodejs.org

```bash
git clone https://github.com/InfinityRichGlobal/HubChat.git
cd HubChat
npm install
```

### ขั้น 2 — สร้างโปรเจกต์ Supabase

1. เข้า supabase.com → **New project**
2. ตั้งชื่อ `hubchat` เลือก region **Southeast Asia (Singapore)** — ใกล้ไทยที่สุด
3. ตั้ง Database Password แล้ว**จดไว้**
4. รอสร้างเสร็จประมาณ 2 นาที

### ขั้น 3 — สร้างตารางทั้งหมด

1. ใน Supabase เมนูซ้าย → **SQL Editor** → **New query**
2. เปิดไฟล์ `supabase/migrations/0001_init.sql` ในโปรเจกต์นี้
3. **คัดลอกทั้งไฟล์** ไปวางในช่อง แล้วกด **Run** (มุมขวาล่าง)
4. ต้องขึ้น `Success. No rows returned`
5. ทำซ้ำกับไฟล์ `supabase/migrations/0002_policy_engine.sql`
6. ทำซ้ำกับไฟล์ `supabase/migrations/0003_messaging_hardening.sql`

> ไฟล์พวกนี้รันซ้ำได้ ไม่พัง ถ้าไม่แน่ใจว่ารันครบ กด Run ใหม่ได้เลย

### ขั้น 4 — ใส่ค่าตั้งระบบ

```bash
cp .env.example .env.local
```

เปิดไฟล์ `.env.local` แล้วเติมค่า :

**จาก Supabase → Project Settings → API**

| ช่องใน .env.local | เอามาจาก |
|---|---|
| `NEXT_PUBLIC_SUPABASE_URL` | Project URL |
| `NEXT_PUBLIC_SUPABASE_ANON_KEY` | anon / public key |
| `SUPABASE_SERVICE_ROLE_KEY` | service_role key (กด Reveal ก่อน) |

**สร้างเองด้วยคำสั่ง** (macOS / Linux เปิด Terminal, Windows ใช้ Git Bash)

```bash
openssl rand -base64 48    # เอาค่าที่ได้ไปใส่ SESSION_SECRET
openssl rand -base64 32    # เอาค่าที่ได้ไปใส่ ENCRYPTION_KEY
```

**บัญชีเจ้าของ** — เติม 3 บรรทัดนี้

```
OWNER_NAME=ชื่อคุณ
OWNER_EMAIL=อีเมลที่จะใช้ล็อกอิน
OWNER_PASSWORD=รหัสชั่วคราว        # เว้นว่างไว้ก็ได้ ระบบจะสุ่มให้
```

### ขั้น 5 — ตรวจว่าต่อติดแล้วสร้างบัญชีเจ้าของ

```bash
npm run check-db      # ต้องขึ้น ✅ ครบทั้ง 26 ตาราง
npm run create-owner  # สร้างบัญชีเจ้าของ — รันได้ครั้งเดียว
```

รันเสร็จแล้ว **ลบ `OWNER_NAME` / `OWNER_EMAIL` / `OWNER_PASSWORD` ออกจาก `.env.local`**

### ขั้น 6 — เปิดใช้งาน

```bash
npm run dev
```

เปิด <http://localhost:3000> → เข้าสู่ระบบด้วยอีเมลกับรหัสชั่วคราว
ระบบจะบังคับให้ตั้งรหัสผ่านใหม่ทันที

## Message Policy Engine (รอบ 2)

### ทำไมต้องมี

Meta มีกฎว่า "ส่งข้อความหาลูกค้าตอนไหนได้บ้าง" และกฎนี้เปลี่ยนบ่อยมาก
ถ้าเขียนกฎกระจายไว้ในหน้าแชท ในบอท ในตัวส่ง follow-up
พอ Meta เปลี่ยนกฎทีต้องไล่แก้ทุกที่ และมักลืมบางจุดจนส่งผิดนโยบาย → เพจโดนระงับ

ระบบนี้จึงรวมกฎทั้งหมดไว้ที่เดียว แล้วบังคับให้ทุกการส่งวิ่งผ่านทางเดียว

### เส้นทางของข้อความ

```
แอดมินกดส่ง / บอทตอบคีย์เวิร์ด / scheduler ส่ง follow-up
                         │
                         ▼
        sendMessage()  ← ทางเข้าเดียว ไม่มีทางอื่น
                         │
                         ├─ 1. กันส่งซ้ำ (idempotency_key)
                         ├─ 2. ดึงข้อเท็จจริงจากฐานข้อมูล
                         │
                         ▼
              Message Policy Engine  ← กฎของ Meta อยู่ที่นี่ที่เดียว
                         │
             ┌───────────┴───────────┐
        ส่งไม่ได้                 ส่งได้
             │                       │
             │                       ▼
             │            เลือก transport ให้เอง
             │            STANDARD → HUMAN_AGENT → UTILITY → MARKETING
             │                       │
             │                       ▼
             │              Transport Adapter (ประกอบ payload)
             │                       │
             │                       ▼
             │              Meta client กลาง  ← ที่เดียวที่ยิง graph.facebook.com
             │                       │
             ▼                       ▼
      บันทึก send_attempts    บันทึก send_attempts
      + เหตุผลภาษาไทย        + retry เฉพาะ error ชั่วคราว
      (ไม่ยิงออกไปเลย)        + แก้ข้อมูลให้ตรงความจริงถ้า Meta บอกว่ากรอบเวลาปิดแล้ว
```

### กฎที่ระบบบังคับให้ ไม่ต้องจำเอง

| กฎ | บังคับด้วยอะไร |
|---|---|
| ทุกการส่งต้องผ่าน engine | มีทางเข้าเดียวคือ `sendMessage()` + eslint + เทสต์สถาปัตยกรรม |
| ห้ามเรียก Meta ตรง ๆ | `graph.facebook.com` มีได้แค่ในไฟล์เดียว มีเทสต์ไล่ตรวจทั้งโปรเจกต์ |
| ห้ามฝังกฎ 24 ชม. ไว้ที่อื่น | ตัวเลขอยู่ใน `policy/config.ts` ที่เดียว มีเทสต์ตรวจว่าไม่มีที่อื่น |
| แอดมินห้ามเลือก transport เอง | API ไม่คืนชื่อ transport ให้หน้าเว็บเลือก มีเทสต์ตรวจ |
| บอท/scheduler ห้ามใช้ `HUMAN_AGENT` | ตรวจ 2 ชั้น (engine + adapter) มีเทสต์ 5 ข้อ |
| ห้ามแปลงข้อความขายให้เนียนเป็นช่องอื่น | ตารางประเภทข้อความต่อช่องทาง มีเทสต์แยกต่างหาก |
| ห้าม retry error เชิงนโยบาย | ตัวแยกประเภท error + เทสต์ครบทุกรหัส |
| ห้ามใช้ message tag แบบเก่า | เทสต์ไล่ตรวจทั้งโปรเจกต์ว่าไม่มีชื่อ tag เหล่านั้น |
| Messenger กับ Instagram ไม่เหมือนกัน | ค่าตั้งแยกกันคนละชุด มีเทสต์ตรวจว่าไม่รั่วถึงกัน |

### ค่าเริ่มต้นคือ "ปิดก่อน"

เปิดใช้แค่การส่งปกติในกรอบเวลาเท่านั้น
ช่องทางที่เหลือปิดไว้หมด และต้องผ่าน 2 สวิตช์ถึงจะใช้ได้ :

1. `..._ENABLED=true` — เปิดใช้
2. `..._VERIFIED=true` — ยืนยันแล้วว่าอ่านเอกสาร Meta และได้รับอนุมัติจริง

ตั้งอย่างเดียวไม่พอ ต้องครบทั้งสอง — กันเผลอเปิดทั้งที่ยังไม่ได้รับอนุมัติ

ดูรายการที่ต้องยืนยันก่อนเปิดได้ที่ `DEFERRED_REVIEW.md`

## ความปลอดภัยของการส่งข้อความ (รอบ 2.1)

หลังตรวจสอบโดยผู้ตรวจอิสระ พบ 4 จุดที่ยังเสี่ยง และแก้แล้วทั้งหมด

### 1. กันส่งซ้ำ — ให้ฐานข้อมูลเป็นคนตัดสิน

เดิมโค้ดทำแบบ "ดูก่อนว่าเคยส่งไหม → ไม่เคย → ยิง → บันทึก"
ถ้าสองคำขอมาพร้อมกัน ทั้งคู่ผ่านด่าน "ดูก่อน" แล้วยิงทั้งคู่ → ลูกค้าได้ข้อความซ้ำ

ตอนนี้ทุกการส่งต้อง **จองสิทธิ์กับฐานข้อมูลก่อน** ผ่านตาราง `message_sends`
ที่มี unique index บนกุญแจกันซ้ำ มีคำขอเดียวเท่านั้นที่จองสำเร็จและได้ยิง
ที่เหลือรู้ตัวทันทีว่าแพ้ และไม่ยิงเลย

> ทดสอบจริงแล้ว: ยิง 5 คำขอพร้อมกันด้วยกุญแจเดียวกัน → Meta ถูกเรียกครั้งเดียว

### 2. กรณีไม่รู้ผล — ห้ามลองใหม่

ถ้าคำขอออกไปแล้วไม่ได้รับคำตอบ (timeout / เน็ตขาด) เราไม่มีทางรู้ว่า Meta รับไปแล้วหรือยัง
การลองใหม่ในสถานการณ์นี้ = ลูกค้าอาจได้ข้อความซ้ำ ซึ่งแก้ไม่ได้

ระบบจึงแยกกรณีนี้ออกมาเป็น `outcome_unknown` : หยุดทันที ไม่ลองใหม่
บันทึกไว้ให้คนเปิดดูเอง แล้วตัดสินใจว่าจะส่งซ้ำไหม

> เราเลือกฝั่ง **"ส่งขาดดีกว่าส่งซ้ำ"** เพราะ Meta ไม่ได้รับประกันว่าจะส่งครั้งเดียวให้เรา

### 3. "คนพิมพ์เอง" ต้องพิสูจน์ได้

เดิมผู้เรียกส่ง `human_typed: true` เข้ามาเองได้ แปลว่าโค้ดอัตโนมัติตัวไหนก็อ้างเป็นคนได้
ซึ่งอันตราย เพราะ `HUMAN_AGENT` ใช้ได้เฉพาะข้อความที่คนพิมพ์จริง

ตอนนี้ต้องใช้ **ตั๋วรับรองแหล่งที่มา** ที่สร้างได้จาก `provenance.ts` ไฟล์เดียว
และตั๋วของ "คน" สร้างได้เฉพาะตอนมี session ของแอดมินตัวจริงเท่านั้น
งานเบื้องหลังไม่มี cookie จึงสร้างไม่ได้โดยธรรมชาติ

### 4. คำตอบของ Meta ห้ามลบประวัติข้อความจริง

เดิมพอ Meta ตอบว่าส่งไม่ได้ ระบบไป **ลบ** `last_customer_message_at` ทิ้ง
นั่นคือการทำลายหลักฐานว่าลูกค้าเคยทักมาเมื่อไหร่ และทำให้รายงานผิดตามไปด้วย

ตอนนี้แยกเป็นสองอย่างคนละตาราง:

| | เก็บที่ไหน | คืออะไร |
|---|---|---|
| ลูกค้าทักมาเมื่อไหร่ | `conversations` / `customers` | **ข้อเท็จจริง** — ห้ามแก้ |
| Meta บอกว่าส่งไม่ได้เมื่อไหร่ | `conversation_policy_state` | **สิ่งที่เราสังเกตเห็น** |

Policy Engine อ่านทั้งคู่: ถ้า Meta เคยปฏิเสธหลังข้อความล่าสุดของลูกค้า → ไม่ส่ง
แต่ถ้าลูกค้าทักกลับมาทีหลัง ข้อสังเกตเก่าถือว่าใช้ไม่ได้แล้ว

### 5. เครื่องจริงเปิดช่องทางที่ยังไม่ยืนยันไม่ได้

ถ้า `NODE_ENV=production` และมี `POLICY_ALLOW_UNVERIFIED_TRANSPORTS=true`
ระบบจะ **ไม่ยอมสตาร์ต** พร้อมบอกวิธีแก้เป็นภาษาไทย

### 6. ข้อมูลต้องสัมพันธ์กันจริง

`sendMessage()` รับแค่ **รหัสห้องแชท** อย่างเดียว
ลูกค้าคนไหน เพจไหน ช่องทางไหน ปลายทางคือใคร — ระบบไปอ่านจากฐานข้อมูลเอง
แล้วตรวจว่าทุกอย่างสัมพันธ์กัน ไม่ตรงข้อเดียวก็ไม่ส่ง

### 7. ตามรอยย้อนหลังได้ครบ

| ตาราง | หนึ่งแถวคือ |
|---|---|
| `message_sends` | การส่งหนึ่งครั้งในเชิงตรรกะ + ผลสุดท้าย + `meta_message_id` |
| `send_attempts` | หนึ่งครั้งที่ยิงออกไปจริง (retry 3 ครั้ง = 3 แถว ไม่ทับกัน) |

ตอบได้ว่า: ส่งอะไร ใช้กุญแจไหน engine ตัดสินยังไง ใช้ช่องทางไหน
ยิงจริงกี่ครั้ง แต่ละครั้งเกิดอะไร Meta ให้ id อะไรมา และจบยังไง
