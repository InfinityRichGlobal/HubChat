# สถานะ HubChat และงานถัดไป

อัปเดต 21 ตุลาคม 2026 — ยืนยันธุรกิจผ่านแล้ว; แก้แพลตฟอร์มเว็บไซต์ใน Meta และการเก็บร่าง Inbox

## ตรวจรอบ 21 ตุลาคม

- แก้หน้าบังคับเปลี่ยนรหัสที่ไม่มีทางออกเมื่อทำรหัสชั่วคราวหาย: เพิ่มลิงก์ออกจากระบบ/ใช้บัญชีอื่นแยกจากฟอร์ม จึงไม่ติดการตรวจช่องรหัสที่ยังว่าง และล้างร่างของบัญชีเมื่อออก ยังคงบังคับเปลี่ยนรหัสก่อนเข้าหน้าที่ป้องกันตามเดิม
- Meta Business Security Center แสดง “ตรวจสอบยืนยันแล้ว” โดยระบุวันที่ 20 ตุลาคม; หน้า Developer แสดงแอพ “เผยแพร่แล้ว” แต่ App Review submission ยังส่งไม่ได้
- พบแพลตฟอร์ม Website ยังไม่มี ทำให้กรอกคำแนะนำผู้ตรวจสอบไม่ได้ เพิ่ม Website URL `https://hubchat-omega.vercel.app/` แล้ว ตรวจหลัง reload ยังคงอยู่
- ยังไม่ได้ส่ง App Review หรือให้ข้อมูลบัญชีเข้าถึงแก่ Meta; ต้องตรวจคำแนะนำผู้ตรวจสอบ หลักฐานฟังก์ชัน และสิทธิ์ที่ขอให้ครบก่อนส่ง
- คอมเมนต์ต้องตรวจสอบ 2 รายการเป็นรายการ 13–14 กันยายน: comment not found และ private reply เกินกรอบเวลา/เคยตอบแล้ว ไม่ล้างข้อผิดพลาดหรือส่งซ้ำเพื่อทำให้ยอดเป็นศูนย์
- แก้ร่างข้อความ: เก็บข้อความใน sessionStorage แยกแอดมินและห้อง อยู่ต่อเมื่อเปลี่ยนหน้า/รีเฟรชในแท็บเดิม อายุข้อมูล 24 ชั่วโมง และล้างเมื่อออกจากระบบ ข้อความอ้างอิงและไฟล์แนบไม่เก็บข้าม reload
- ถ้า browser ปิดกั้น storage ยังพิมพ์ต่อในหน่วยความจำได้และแจ้งให้ทราบว่าเก็บข้ามรีเฟรชไม่ได้
- รอบนี้ typecheck, unit 688/688, lint และ build ผ่าน; check-db ผ่าน 40 ตาราง ไม่มี migration ใหม่ ชุด PostgreSQL 318 ข้อเป็นหลักฐานรอบก่อน ไม่ได้รันซ้ำในรอบแก้ browser storage

## รอบปรับการใช้งานและความครบถ้วนของข้อมูล

- Inbox: แยกหัวข้อ/ค้นหา/กลุ่มงานให้ชัด ใช้สีหลักน้ำเงิน ปรับจอเล็ก 320/390px และเดสก์ท็อป แสดงข้อผิดพลาดโหลดรายการพร้อมปุ่มลองใหม่
- ป้องกัน effect โหลดรายการวนซ้ำเมื่อเปิดห้องที่อยู่นอกผลตัวกรอง และยกเลิกคำขอเก่าเมื่อเปลี่ยนตัวกรอง
- ตัวกรองแพลตฟอร์ม ผู้ดูแล และจำนวนออเดอร์ทำงานบน server ก่อนแบ่งหน้า จึงค้นพบรายการนอก 50 ห้องแรก; เพจที่ไม่มีสิทธิ์คืนรายการว่าง
- นับออเดอร์แบบแบ่งหน้า ไม่ตัดที่ 1,000 แถว และไม่นับรายการยกเลิก/คืน
- เก็บร่างข้อความและข้อความอ้างอิงเมื่อสลับห้องในหน้า Inbox; รอบ 21 ตุลาคมเพิ่มการเก็บข้อความข้ามรีเฟรช/เปลี่ยนหน้าในแท็บเดิมแล้ว
- Comments: การ์ดยอดรอจัดการ/ต้องตรวจผลกดกรองได้ รายละเอียดมีปุ่มก่อนหน้า/ถัดไปพร้อมลำดับ และกันการเปลี่ยนรายการขณะมีร่างค้าง
- แจ้งเตือนอ่านห้องต่อจาก 200 รายการแรก และแบ่งหน้าประวัติคำตอบแอดมิน ป้องกันทั้งการตกหล่นและการเตือนห้องที่ตอบแล้ว
- PostgreSQL regression ผ่าน 318 tests / 19 files รวมกรณี 205 ห้องและประวัติคำตอบมากกว่า 1,000 รายการ; unit ผ่าน 684 tests / 35 files
- ทดสอบ UI ด้วยข้อมูลจำลอง ไม่ส่งข้อความหรือคอมเมนต์ถึงลูกค้าจริง ไม่มี migration ใหม่ในรอบนี้
- ขอบเขตที่ยังไม่รับรอง: โหลดระดับสูงมากยังต้องทดสอบเวลา worker และขนาดตัวกรองจำนวนมาก; ผลทดสอบนี้ไม่แทนการรับส่ง Facebook/Instagram จริงหลังสิทธิ์พร้อม

## งานรอบ 20 ตุลาคม

- ยังไม่มี webhook ใหม่หลังคิว #89 วันที่ 18 ต.ค. จึงยังไม่ยืนยัน real-time จากลูกค้าจริง
- เห็นสถานะ Business Verification เป็น “อยู่ระหว่างการตรวจสอบ” ใน Meta แล้ว ผู้ใช้ส่งเอกสารเอง ไม่ต้องเริ่มยื่นใหม่
- ตรวจร่าง App Review พบ 20 รายการ รวมสิทธิ์ Instagram คนละเส้นทางและฟีเจอร์ที่ยังไม่มีหลักฐานสาธิต จัดทำ [ชุดเตรียม App Review](META_APP_REVIEW_TH.md) พร้อมคำอธิบายภาษาอังกฤษและสคริปต์คลิป ไม่ได้เปลี่ยนสิทธิ์หรือส่งคำขอ
- ปรับหน้า Privacy ให้ตรงกับข้อมูลจัดส่ง/สลิป, URL สื่อสาธารณะ, Telegram/Web Push, Gemini และขั้นตอนตรวจคำขอลบข้อมูล รุ่น `a1ffb5a` ขึ้น production Ready แล้ว
- ตรวจรอบนี้: typecheck ผ่าน, unit 684/684 ผ่าน, lint ผ่านไม่มี warning และ production build ผ่าน; เปิดหน้า Privacy ในเครื่องได้ HTTP 200 และตรวจเนื้อหา/ภาพจริงแล้ว

- [x] กันตอบคอมเมนต์ซ้ำทั้งบอทและแอดมิน: ใช้การจองในฐานข้อมูลร่วมกัน เก็บ fingerprint ของคำตอบ กดซ้ำหรือเปิดหลายแท็บไม่ยิงซ้ำ ผลไม่แน่นอนคงสิทธิ์ไว้ให้ตรวจต้นทาง บันทึกผลล้มเหลวไม่รายงานเป็นสำเร็จ

- ตรวจมือถือ 320px และ 390px: ลูกค้า, ประวัติส่ง, Inbox, Settings และกล่องยืนยันคำขอลบข้อมูลไม่ล้นแนวนอน
- ทดสอบหน้าคำขอลบถึงกล่องยืนยันแล้วกดยกเลิก การลบจริงทดสอบเฉพาะ PostgreSQL จำลอง ไม่มีการลบหรือส่งข้อความถึงลูกค้าจริงระหว่าง QA
- Comments รุ่นก่อนขึ้น production commit `2c85cc8` และตรวจตัวกรอง/ร่าง/มือถือจริงไว้แล้ว

## การนำขึ้นระบบรอบนี้

- ลง migration 3 ไฟล์ `20261019_data_deletion.sql`, `20261019_runtime_reliability.sql`, `20261019_worker_schedule.sql` ผ่าน SQL Editor แบบ transaction สำเร็จ และ check-db จริงผ่าน
- Deployment โค้ดหลัก `f74139f` และการเชื่อม scheduler รุ่น `98e3ec2` ขึ้น Vercel Ready บน production แล้ว
- พบ production ยังไม่มี CRON_SECRET ที่ใช้งานได้ จึงบันทึกค่าของโปรเจกต์แบบเข้ารหัส และเชื่อม Vault จาก Settings ด้วยค่าที่ production อ่านเอง
- Scheduler กู้คิวเรียกจริงสำเร็จตั้งแต่ 00:52 น. วันที่ 19 ตุลาคม (HTTP 200, งานรอ 0) การตรวจเส้นทางด้วย bearer เดียวกันได้ 200 เช่นกัน

- ตรวจ production: Settings/คำขอลบข้อมูล/ลูกค้า/Comments ผ่าน ประวัติส่งหน้า 1 แสดง 50 รายการ หน้า 2 แสดงอีก 8 รายการ ปุ่มก่อนหน้า/ถัดไปถูกต้อง

## งานภายนอกที่ยังต้องยืนยัน

1. Business Verification ผ่านแล้ว; App Review ยังไม่ส่ง ต้องคัดสิทธิ์ที่ใช้จริง เตรียมบัญชีตรวจเฉพาะและคลิปจริงตาม META_APP_REVIEW_TH.md ก่อนเผยแพร่แอป
2. หลังสิทธิ์พร้อม: ทดสอบ Facebook และ Instagram จากบัญชีจริง ตาม event → webhook → queue → DB → ตอบเพียงครั้งเดียว พร้อมเวลาและผลบนหน้าลูกค้า ปัจจุบันมีหลักฐาน webhook ตัวอย่างถึงระบบ แต่ยังไม่ยืนยันข้อความจริงจากผู้ใช้ทั่วไปครบวงจร
3. การรับ Telegram/Web Push บนอุปกรณ์จริงต้องให้ผู้รับตรวจว่าถึงและได้รับอนุญาตจากอุปกรณ์แล้ว ผล worker หรือชุดทดสอบไม่แทนหลักฐานปลายทางนี้

ผลผ่านในเอกสารนี้หมายถึงขอบเขตที่มีหลักฐานทดสอบ ไม่ใช่การรับรองว่า Meta หรืออุปกรณ์ภายนอกพร้อมทั้งหมด รายละเอียดทางรับข้อมูลรอบก่อนอยู่ใน [META_DELIVERY_REPAIR_TH.md](META_DELIVERY_REPAIR_TH.md)
