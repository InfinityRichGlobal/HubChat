# ดูแลคิวและคำขอลบข้อมูล

อัปเดต 19 ตุลาคม 2026

## งานเบื้องหลังบน Production

ระบบรับ webhook แล้วแยกเป็นงานละเหตุการณ์ บันทึกครบก่อนตอบ Meta และประมวลผลหลังตอบ HTTP ตัวกู้คิวบน Supabase เรียก `/api/ingest/process` ทุกนาที ส่วน `/api/notify/flush` ทำงานทุก 5 นาที ไม่ต้องเปิดเครื่องผู้พัฒนาค้างไว้ ยกเลิก Vercel cron รายวันเดิมเพื่อไม่ให้ซ้อนกับตารางนี้หรือใช้ token เก่าจาก deployment

- Migration: `20261019_runtime_reliability.sql`, `20261019_worker_schedule.sql`
- ต้องมี `pg_cron`, `pg_net`, `supabase_vault` บน Supabase
- ตั้งครั้งแรกหรือเมื่อเปลี่ยนคีย์ผ่าน Settings → “เชื่อมตารางเวลาอัตโนมัติ” บนโดเมน production เซิร์ฟเวอร์อ่าน `CRON_SECRET` ของ deployment แล้วบันทึกใน Vault ผ่าน RPC `configure_worker_schedule(p_app_url,p_token)` ไม่ส่งคีย์กลับ browser และไม่ใช้คีย์ของเครื่อง local ซึ่งอาจต่างกัน ห้ามใส่ค่าจริงใน SQL Editor, Git, เอกสาร หรือข้อความแชท
- ปลายทางใช้ HTTPS origin ของ deployment จริง Token ต้องตรงกับค่าที่ API ใช้ เมื่อเปลี่ยน token หรือโดเมน ให้เรียกตั้งค่าใหม่
- Token เก็บใน Vault ชื่อ `hubchat_worker_token`; URL ชื่อ `hubchat_worker_url` ตาราง `cron.job` มีเพียงคำสั่งเรียกฟังก์ชัน
- `worker_schedule_status()` คืนชื่อ/ตารางเวลา/สถานะ ไม่มีความลับ
- เจ้าของตรวจใน Settings → คิวรับข้อมูลและงานเบื้องหลัง: เวลาสำเร็จล่าสุด งานรอ งานที่ลองครบแล้ว และข้อผิดพลาด
- การมีตารางเวลาหรือ heartbeat ไม่ยืนยันว่าลูกค้าจริงส่งข้อมูลมาถึง Meta webhook แล้ว ต้องดูหลักฐาน event ของการทดสอบจริงร่วมกัน

## เมื่องานล้มเหลว

งานลองใหม่มีช่วงรอเพิ่มจาก 15 วินาที สูงสุด 15 นาที การจองงานมีเลข attempt กำกับ worker เก่าจึงเขียนทับผลของ worker ใหม่ไม่ได้ งานที่โปรเซสหยุดในครั้งสุดท้ายจะเปลี่ยนเป็นล้มเหลวแทนค้างตลอดไป

หลังแก้สาเหตุ ให้เจ้าของกด “ลองใหม่หลังแก้สาเหตุ” ใน Settings ระบบสร้างงานใหม่และเชื่อมกับงานเดิม กดซ้ำไม่สร้างหลายงาน ห้ามแก้ attempts/status ในฐานข้อมูลเพื่อข้ามกลไกนี้

ถ้าส่งข้อความหรือคอมเมนต์แล้วไม่ทราบว่า Meta รับหรือไม่ ให้ตรวจต้นทางก่อน ระบบจะกันส่งซ้ำไว้ การ timeout ไม่ใช่หลักฐานว่าส่งไม่สำเร็จ งานเก่าที่ถูกลบข้อมูลส่วนตัวแล้วจะไม่อนุญาตให้ replay

## คำขอลบข้อมูล

Callback `/api/webhooks/meta/data-deletion` (และ `/api/meta/data-deletion` เดิม) ตรวจลายเซ็น Meta แล้วบันทึกคำขอจริง รหัสสถานะที่ไม่พบคืน 404 ไม่รายงานว่าลบเสร็จโดยไม่มีหลักฐาน

เจ้าของเข้า Settings → คำขอลบข้อมูล เพื่อตรวจตัวตน เลือกลูกค้า/คอมเมนต์ที่สัมพันธ์กัน บันทึกหลักฐานแบบไม่ใส่รหัสผ่านหรือเลขเอกสาร แล้วตรวจกล่องยืนยันก่อนดำเนินการ รหัสผู้ใช้ระดับแอปของ Meta ไม่ใช่ PSID ของลูกค้า จึงห้ามจับคู่ด้วยการเทียบเลขอย่างเดียว

ระบบลบไฟล์ที่จดทะเบียนและเชื่อมกับรายการที่เลือกก่อน จากนั้นลบข้อมูลที่เกี่ยวข้องใน transaction เดียว (แชท ออเดอร์ ประวัติส่ง คอมเมนต์ บันทึกแจ้งเตือนและข้อมูลนำเข้าที่สัมพันธ์กัน) หากไฟล์ถูกใช้ร่วมกับลูกค้าคนอื่นจะหยุดให้ตรวจ เจ้าของต้องตรวจสำเนาภายนอกและข้อมูลที่ไม่เชื่อมโยงเพิ่มเติม

- Storage หรือ DB ล้มเหลว: สถานะ failed และลองคำขอเดิมได้ โดยใช้ขอบเขตที่ตรวจไว้เดิม
- งานยัง processing: กันการทำซ้อน 10 นาที แล้วเปิดให้กู้คำขอที่ค้าง
- เสร็จจริงจึงเป็น completed และเก็บผลจำนวนที่ลบ พร้อมล้างรหัสผู้ใช้ที่เข้ารหัสและรายการไฟล์ใน manifest
- เก็บเฉพาะ hash แยกเพจและเวลาลบ เพื่อป้องกัน webhook เก่ากู้ประวัติที่ลบกลับมา ข้อความใหม่หลังเวลานี้ยังรับได้
- ไม่ควรทดสอบการลบกับลูกค้าจริง ใช้ `tests/pg/compliance.pg.test.ts` บนฐานข้อมูลทดสอบ

## ก่อนส่งต่อผ่าน Git

อ่าน `AGENTS.md` และเช็ก `git status` ก่อนแก้ไข จากนั้นรัน `npm run typecheck`, `npm test`, `npm run lint`, `npm run build`, `npm run check-db` และชุด PostgreSQL เมื่อแก้ transaction/คิว/สิทธิ์

`test:pg` ต้องต่อ PostgreSQL ที่เปิดไว้และไม่ skip เงียบ ๆ คำสั่ง reset จำกัดให้ใช้ host local กับชื่อฐาน `hubchat_*test` เท่านั้น ห้ามชี้ตัวทดสอบไป production

ผลทดสอบครอบคลุม Meta/Storage/Telegram/Web Push ที่จำลองตามสัญญาของ API การส่งถึงอุปกรณ์และบัญชีภายนอกจริงต้องยืนยันต่างหาก
